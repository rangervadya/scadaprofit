# Диагностика Qwen/Ollama · версия 4.2.7

## 1. Проверить реальное состояние

Откройте:

```text
http://АДРЕС-СЕРВЕРА:3001/api/health
```

Нужны значения:

- `ollama.reachable: true` — приложение может обратиться к Ollama.
- `ollama.modelInstalled: true` — выбранная модель действительно установлена.
- `ollama.models` — список доступных локальных моделей.

## 2. Если модель не установлена

```bash
docker compose up -d ollama
docker compose exec ollama ollama pull qwen3-vl:4b
docker compose restart app
```

Или запустите `./install-qwen-model.sh` из каталога проекта.

## 3. Если Ollama недоступна

```bash
docker compose ps
docker compose logs --tail=150 ollama
docker compose logs --tail=150 app
```

При использовании Ollama непосредственно на хосте проверьте:

```bash
ollama list
curl http://127.0.0.1:11434/api/tags
```

В Docker-приложении адрес хоста должен быть указан через `host.docker.internal` и `compose.host-ollama.yaml`; `127.0.0.1` внутри контейнера app указывает на сам контейнер app, а не на хост. Если Ollama и приложение запущены напрямую на одной машине, `127.0.0.1:11434` подходит.

## 4. Если модель доступна, но маршрутов 0

Откройте экспорт JSON и найдите объект `semanticTrace`. Версия 4.2.6 указывает, получила ли модель пустой массив, вернула ли неверный формат, не прошли ли маршруты фильтр длины/координат или закончился тайм-аут.

Если `available=true`, но `raw_routes=0`, значит Ollama ответила, а сама модель не извлекла маршруты из изображения. Это не проблема подключения; используйте более чёткий скан или разделите большую схему на отдельные фрагменты. Не считайте слой `DETAIL_REVIEW` подтверждённой геометрией труб.

## 5. Пустой ответ без HTTP-ошибки

В версии 4.2.7 `graph.json` включает массивы `ocr.qwen.tile_diagnostics` и `semanticTrace.tile_diagnostics`. Для каждого успешного запроса они показывают `done_reason`, `eval_count`, `prompt_eval_count`, `json_keys`, `raw_annotations` или `raw_routes`, а также число принятых объектов. Если `successful_tiles` равно числу `tiles`, но все `raw_routes`/`raw_annotations` равны нулю, Ollama и модель отвечают, но не распознают содержимое изображения. Если `done_reason` равно `length`, модель достигла лимита генерации; если у плитки есть `error`, проверьте его отдельно. Текст ответа не сохраняется в диагностике.

Трубная трассировка выполняется фрагментами 3×3 с перекрытием 14%; каждая полилиния обрезается по сердцевине своей плитки, поэтому зоны перекрытия не должны давать повторные линии в DXF.

## 6. Интерпретация диагностики 4.2.6 и изменения 4.2.7

В журнале 4.2.6 были зафиксированы два разных результата:

- `semanticTrace.tile_diagnostics`: `done_reason=stop`, `eval_count=5` или `8`, `json_keys=["routes"]`, `routes_key_count=0`. Это не тайм-аут и не отбрасывание по confidence: модель завершила ответ и сразу вернула пустой массив.
- `ocr.qwen.tile_diagnostics`: `done_reason=length`, `eval_count=1024` на каждой плитке. Это означает, что ответ достиг старого лимита OCR и мог быть усечён.

В 4.2.7 запросы используют JSON Schema в параметре Ollama `format`. OCR-схема требует `annotations[]`, схема труб — `routes[]`, где каждый элемент содержит две точки одного прямого отрезка. OCR и pipe token budgets по умолчанию — 2048. Если после этого `routes` снова пусты при `done_reason=stop` и малом `eval_count`, модель всё ещё не распознаёт трубные штрихи на этом изображении; это не исправляется тайм-аутом. Если `done_reason=length`, проверьте `truncated` и количество токенов.
